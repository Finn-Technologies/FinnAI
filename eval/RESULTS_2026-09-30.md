# FinnAI eval — before/after Phases 1-3 (Xiaomi, 2026-09-30)

Two runs of the same 29-case suite on the same phone
(SD778G, `QTI SM7325 qcom lisa/8c/7GiB`, 4096 ctx), the second against
the Phase 1/2/3 tree. The "before" run is commit `2390524`.

The baseline *files* were not recovered — the app was replaced before
`releaseMemory()` completed, and the file each run wrote to external
storage went with it. These are the `FINN_EVAL_SUMMARY` /
`FINN_EVAL_GATE` log lines, which are the same numbers a baseline file
records. The second run was on a cool phone; the first was not, which is
called out below where it matters.

## Reading these

**The two headline wins are real.** Empty replies halved and the
4000-token runaway is gone — that one was a 230-second case, nearly four
times the rest of the suite put together, and the inverted output budget
is what allowed it. TTFT p95 more than halved, which is the user-visible
number: a 2-token answer no longer takes nine seconds.

**Browse recall was already 0 and stayed 0.** The search policy's trigger
lists are keyword-based and none of the suite's "needs the web" prompts
match them. Phase 3 *suppressed* searches (closed-domain facts, follow-ups)
and could not have raised recall; it is not a regression and it is not a
fix. Real browse recall needs the decision pass to be trusted on prompts
that do not contain the word "search", which is Phase 1's grammar
question, still open.

**Everyday went 0.00 → 0.33 and factual went 0.67 → 0.33.** The everyday
improvement is the one that matters most — that is the audience the
product is for. The factual drop is the price of the search suppression:
those cases now answer from the model's own knowledge, which is right for
"what is the capital of France" and wrong for anything the model has
stale or missing. It is a real trade, not a free win, and the fix is
better recall rather than reverting the suppression.

**Check pass rate moved −2.4pp**, which is within the noise of a 3-case
suite on a phone that throttles. I would not read it as a regression.

**Decode tok/s is not a clean comparison.** The first run ended with the
phone at 41°C after ~50 minutes of sustained load; the second started
cool. The +14% is at least partly the phone, not the code.

**Empty replies are still 4x the bar.** 8.6% against a 2% target. The
streaming fix removed the ordering race; what remains is something else
and Phase 1's engine-side work has not yet been measured against it.

The suite is honest about this: two of three gates fail, and the run is
marked `"passed": false`. A baseline that reported a pass here would be
worse than no baseline.

## Caveats

- Non-Latin prompts were not in either run (that is the separate
  `eval/prompts/multilingual.json` pass, still deferred).
- One case per run is a browse case, so "browse recall 0.0" is one
  observation, not a rate.
