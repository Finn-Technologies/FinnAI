# FinnAI eval — after the search rewrite (Xiaomi, 2026-09-30)

Device: SD778G, 7 GiB. Same suites as [RESULTS_2026-09-30.md](RESULTS_2026-09-30.md),
now run through the app's own search step (`SearchPlanner` → `SearchTurn`) instead of the
engine alone, with five more must-browse cases and one image case. Baselines committed:
`baseline_Abhi-Flex1-device.json` (standard policy, 4096 ctx, 40 turns) and
`baseline_lite.json` (forced Lite policy, 2048 ctx, image case, 41 turns).

All three gates pass on both policies.

## What the numbers mean

* **Empty replies 8.6% → 0%.** The base system prompt advertised `browser_search/open/find`
  on every turn. Only "advanced" prompts had a loop to run them; every other turn emitted a
  call into its answer and the output filters swallowed it. The same defect is the reported
  "looping on tool calls". Removing the advertisement fixed both (ADR 0001).
* **Browse recall 0.0 was a measurement bug.** The eval bypassed the app's search step.
  With the planner in the path recall is 1.0 on six must-browse prompts (was one).
* **Precision needed a real fix.** Run through the planner, 76% of must-not-browse turns
  searched, because every wh-question did. Generic explanations and how-tos now stay local;
  a question that names a person, place or year still browses.
* **Lite text-only load works.** The image case answered correctly ("42") on a device policy
  that loaded no projector, after one reload: TTFT 16.3 s (reload + 9.6 s prefill at 2048 ctx).
  That first-image cost is accepted (ADR 0004); later images on the same runtime skip the reload.

## Not good yet

* **Searching turns cost 8-12 s TTFT** (5 s search budget + prefill of the grounded prompt).
  Overlapping the search with model load and trimming the grounded context are the next levers.
* **Check pass rate is 65-75%.** Most failures are length checks ("is 1-15 words"): the model
  is more verbose than a "brief" prompt allows. That is a style/sampler problem, not a
  reliability one, and is not addressed here.
* **`everyday.upgrade_laptop_ram` and `adversarial.harmful_refusal` still fail their content
  checks** on some runs.
* The forced-Lite run measures the Lite *policy* on a 7 GiB phone. It is not a 4 GB device:
  peak RSS and thermals on real low-end hardware are still unmeasured.
